## 4. APK 與評審體驗

### 優先風險：健康資料與測試資源

既有 Demo 前置要求當日步數至少 8,000，以及足夠 tSKR。新安裝的評審可能沒有健康資料、測試代幣或符合 NFT 領取條件。專案排除手動與部分第三方步數來源，不能假設手動補登即可通過驗證。

需決定並驗收以下體驗安排：

1. 一般路徑：自己的錢包 → Health Connect 授權 → 真實健康資料 → 打卡。
2. 無健康資料的體驗方式：列明仍可操作的功能；若新增示範資料模式，必須清楚標示，與真實健康驗證隔離，說明哪些資料模擬、哪些交易實際上鏈。此模式目前僅為建議，不代表已實作。
3. 評審指南：Android 版本、相容錢包、Devnet 設定、測試 SOL／tSKR 取得方式、已知限制與失敗恢復方式。不得公開團隊測試錢包私鑰。

### 建置方式

依現有流程，在正式 keystore 與 demo 環境準備完成後，於專案根目錄執行：

```bash
source scripts/env.sh
scripts/app/build.sh demo release
```

預期產物：`app/android/app/build/outputs/apk/release/app-release.apk`。

使用專案建置腳本；目前 Gradle 在缺少 release 設定時有 debug 簽章 fallback，而專案腳本會阻擋缺少 keystore 的 release 建置。最終仍需檢查產物憑證。keystore 與密碼不提交至 Git。

## 6. 建議 Demo 分鏡（三分鐘）

核心主線：日常打卡；第二亮點選成就 NFT。若主打賽事，可用賽事替換 NFT 段落，不增加總段落。三分鐘是製作目標，需依 RULE-02 調整。

| 時間 | 畫面／操作 | 傳達重點／驗收注意 |
|---|---|---|
| 0:00–0:15 | 手持 Seeker，展示今日任務 | 每日運動如何變成可驗證成就 |
| 0:15–0:40 | 連接錢包，簡短呈現健康授權 | 真正的手機與錢包整合 |
| 0:40–1:35 | 已達標步數 → Clock in → 必要檢查與簽名 → 交易確認 | 主流程保留最多篇幅，依實際簽名次數呈現 |
| 1:35–1:50 | 獎勵／狀態更新，開 Explorer | 交易成功、cluster 正確、地址與 App 相符 |
| 1:50–2:15 | 已符合資格的成就 NFT 領取 | 標明事先累積進度，展示真正領取結果 |
| 2:15–2:35 | 藝廊或既有賽事排行榜 | 明天、下週再回來的理由 |
| 2:35–2:50 | 一張架構圖 | 原始健康資料留手機、後端驗證摘要、鏈上記錄結果 |
| 2:50–3:00 | Roadmap 與產品收尾 | 現在可用功能與下一步驗證方向 |

### 錄影注意事項

- 準備兩個團隊控制的測試錢包：一個當日未領獎，一個已符合成就資格；不要公開私鑰。
- 先核對 UTC 任務日，避免彩排先領完，正式錄影無法再次打卡。
- 備妥足夠測試 SOL；若展示賽事，另備足夠 tSKR。
- 登入簽名、claim challenge 簽名、交易簽署可能是不同步驟，不統稱「一次簽名」。
- 新帳號不一定一次打卡就升級或可領 NFT；預先準備的進度、不同帳號與不同場次必須標註。
- 升級動畫要確認由真實狀態驅動；純預覽動畫不能作為已完成升級交易的證據。
- 不將報名與結算剪成同一場賽事立即完成；跨場次／跨時間清楚註記。
- 全程清楚標示 Devnet；tSKR 為無金錢價值測試代幣，非官方 SKR。
- 建議英文字幕；等待段可剪輯，但不得改變交易成敗或等待時間的實際意義。
- 靜態截圖僅為補充或備援；主片應展示實際操作。測試數量以錄影時可驗證的結果為準。
