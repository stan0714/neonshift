## 0. 文件規劃說明（本版與 v0.1 的差異）

v0.1 是一段式的概念摘要，具備清楚的產品願景、四大核心機制、三項代幣機制與四週時程，但缺少可供開發、測試與評審對照的細節。本版依下列原則擴充：

1. **每個功能都有編號、優先級與驗收條件**，讓四週衝刺可直接切成任務。
2. **把 v0.1 的技術前提修正為可執行方案**（詳見第 10 章與附錄 A）。
3. **代幣經濟給出具體參數與公式**，避免在第三週「微調發放參數」時沒有基準。
4. **明確列出範圍外項目、風險、待決事項與提交清單**，這些是評審與 dApp Store 審核最常卡關的地方。
5. **平台範圍收斂為 Android 單一平台**（v0.3 新增），移除所有 iOS 與跨平台的條件式敘述，讓需求、測試與時程只需針對一組平台撰寫。

## 2. 專案背景與業務目標

### 2.1 背景【原文】
NeonShift 是一款專為 Solana Mobile 打造的「賽博融合（Cyber-Fusion）」健康追蹤 App。將日常運動轉化為賽博特工在虛擬網路中的「打卡（Clock In）」任務，透過手機硬體健康數據與 Solana 低延遲特性，讓每一步成為驅動數位資產增長的能量。

### 2.2 業務目標

| 編號 | 目標 | 衡量方式 |
|---|---|---|
| BG-01 | 獲得 $10,000 SKR「最佳 Solana Mobile Stack 整合」獎【原文】 | 評審結果 |
| BG-02 | 於 2026-10-08 前完成 dApp Store 提交【原文】 | 提交紀錄 |
| BG-03 | 展示「手機硬體 × Solana」的獨特整合（Health Connect、感測器、MWA、Seed Vault） | Demo 影片涵蓋四項整合 |
| BG-04 | 建立可持續的 SKR 消耗（Sink）與產出（Emission）閉環 | 第 8 章參數與模擬結果 |
| BG-05 | 【假設】提交後 30 天內達成 500 位錢包連線使用者 | 鏈上唯一錢包數 |

### 2.3 差異化定位
- 「無感」：不需手動記錄，背景同步健康數據。
- 「可驗證」：以硬體感測器交叉驗證防作弊，是主要技術賣點。
- 「有資產感」：動態 NFT 跑鞋隨真實運動進化。
- 「Seeker 原生」：MWA 一鍵簽章、Seed Vault 安全金鑰、dApp Store 分發。

## 5. 範圍定義

### 5.0 平台範圍（決策 D-04）【已確認】

**本專案只開發 Android 原生行動應用，目標裝置為 Solana Mobile Seeker。iOS 不在本次範圍內，且不保留 iOS 相容性設計。**

| 項目 | 決定 |
|---|---|
| 開發平台 | Android 單一平台 |
| 主要測試裝置 | Solana Mobile Seeker |
| 次要測試裝置 | 任一 Android 14 以上手機（用於驗證 Health Connect） |
| iOS | 不開發、不測試、不預留介面抽象層 |
| 建置產物 | Android APK / AAB（單一目標） |

理由：

1. Mobile Wallet Adapter 因 iOS 系統限制不支援 iOS，缺少它就無法達成本專案的核心賣點與 BG-01 的評獎條件。
2. Health Connect 為 Android 專屬平台，iOS 需改接 HealthKit，等於兩套健康資料層。
3. dApp Store 分發本身即為 Android 通道。
4. 四週衝刺時程下，單一平台可將全部工時投入深度整合而非跨平台相容。

影響：React Native 專案僅維護 `android/` 目錄，不需 `ios/` 建置設定；套件選型不必考慮 iOS 支援；測試計畫、CI 與驗收條件皆以 Android 實機為準。

### 5.1 範圍內（In Scope）
- Android App（React Native），單一平台，以 Solana Seeker 為主要目標裝置。
- Health Connect 步數與睡眠讀取。
- MWA 錢包連線、交易簽章。
- 每日打卡與 SKR 獎勵發放（devnet，使用測試用 SKR 代幣）。
- 動態 NFT 跑鞋（鑄造、等級、外觀進化）。
- 裝備升級（SKR 消耗）。
- 週末步數馬拉松錦標賽（質押、排名、獎金分配）。
- 硬體級防作弊（陀螺儀 + GPS + 資料來源檢查）。
- 賽博龐克風 UI。
- Demo 影片、Pitch 文件、dApp Store 提交。

### 5.2 範圍外（Out of Scope）
- **iOS 版本、Apple HealthKit 串接，以及任何為 iOS 預留的跨平台抽象層**（見 5.0 決策 D-04）。
- Google Fit API（已停止新申請，2026 年底關閉）。
- 主網（mainnet）部署與真實 SKR 發放。
- 社交功能（好友、聊天、分享）。
- NFT 二級市場交易。
- 穿戴裝置（Wear OS）直接整合。
- 多語系（首版僅英文介面，【待確認】是否需要繁中）。

## 6. 使用者旅程

### 6.1 首次使用（Onboarding）
1. 安裝並開啟 App，看到賽博龐克風歡迎畫面。
2. 點擊「連線錢包」，MWA 喚起 Seeker 錢包並授權。
3. 系統請求 Health Connect 步數、睡眠與背景讀取權限，並請求定位與活動辨識權限。
4. 完成後自動鑄造初階跑鞋 NFT（Lv.1，灰階光條）。
5. 進入主儀表板，顯示今日步數、睡眠、任務進度。

### 6.2 每日打卡
1. App 在背景或開啟時同步 Health Connect 資料。
2. 達成 8,000 步或 7 小時睡眠後，儀表板出現「可打卡」狀態。
3. 使用者點「Clock In」，App 送出健康數據與感測器摘要到後端驗證。
4. 後端回傳簽章證明，App 組交易並經 MWA 簽章送鏈。
5. 交易確認後 SKR 入帳，跑鞋經驗值增加，霓虹特效播放。

### 6.3 裝備升級
1. 進入「裝備」頁面查看跑鞋等級與數據核心。
2. 選擇升級，顯示所需 SKR 與升級後倍率。
3. 確認並簽章，SKR 燒毀或轉入國庫，NFT metadata 更新，外觀進化。

### 6.4 週末錦標賽
1. 週五開放報名，質押固定數量 SKR。
2. 週六 00:00 至週日 23:59 累積步數計入排名。
3. 週一結算，前段班瓜分獎金池，其餘玩家取回部分質押（見 8.4）。

## 8. SKR 代幣經濟模型

### 8.1 總覽【原文】

| 系統機制 | 代幣流向 | 說明 |
|---|---|---|
| 日常任務打卡 | 產出 | 達成每日 8,000 步或 7 小時睡眠，系統自動發放基礎 SKR |
| 裝備進階升級 | 消耗 | 支付 SKR 升級跑鞋「數據核心」，提升未來產出倍率 |
| 賽季錦標賽 | 消耗／獎勵 | 質押 SKR 參與週末步數馬拉松，前段班瓜分獎金池 |

### 8.2 產出公式【假設】

```
每日獎勵 = 基礎獎勵 × 核心倍率 × 連續加成
基礎獎勵：步數任務 10 SKR，睡眠任務 5 SKR（兩者可同日各領一次）
核心倍率：見 8.3
連續加成：連續 7 天以上 1.1，否則 1.0
單錢包每日上限：40 SKR
```

黑客松期間使用 devnet 上自行鑄造的測試 SKR（Mint 由團隊持有），總發行上限【假設】1,000,000，獎勵金庫預先撥入 200,000。

### 8.3 數據核心升級表【假設】

| 核心等級 | 倍率 | 升級成本（SKR） | 累積成本 | 純步數任務回本天數 |
|---|---|---|---|---|
| 1 | 1.0 | — | 0 | — |
| 2 | 1.2 | 30 | 30 | 15 |
| 3 | 1.5 | 60 | 90 | 20 |
| 4 | 1.8 | 100 | 190 | 21 |
| 5 | 2.2 | 160 | 350 | 22 |

設計原則：回本天數隨等級上升，避免高等級玩家無限加速；升級成本 70% 燒毀、30% 進入錦標賽獎金池【待確認】。

### 8.4 錦標賽規則【假設】

| 項目 | 參數 |
|---|---|
| 報名質押 | 50 SKR |
| 比賽時段 | 週六 00:00 至週日 23:59（UTC） |
| 獎金池 | 全部質押 × 80% + 國庫挹注 |
| 前 10% | 瓜分獎金池 60%（依名次遞減） |
| 前 11% 至 30% | 瓜分獎金池 40% |
| 其餘 | 取回質押 × 50% |
| 作弊者 | 質押全數沒收進入獎金池 |

### 8.5 經濟健康檢查
第三週需以試算表模擬 100 位使用者 30 天的產出與消耗，目標消耗／產出比 ≥ 0.6，並將模擬結果放入 Pitch。

## 9. 系統架構與技術需求

### 9.1 元件

| 元件 | 技術 | 職責 |
|---|---|---|
| 行動 App（Android only） | React Native（Expo 或 bare，僅建置 Android 目標）、@solana-mobile/mobile-wallet-adapter-protocol、react-native-health-connect、expo-sensors、expo-location | UI、健康數據讀取、感測器摘要、交易組裝與簽章 |
| 驗證後端（Attestor） | Node.js 或 Rust、PostgreSQL | 接收健康與感測器資料、執行防作弊規則、簽發 ed25519 證明、維護排行榜 |
| 鏈上程式 | Anchor（Rust） | 驗證證明、防重複打卡、發放 SKR、記錄跑鞋狀態、錦標賽質押與結算 |
| NFT | Metaplex Core（或 Token Metadata） | 跑鞋 NFT 鑄造與 metadata 更新 |
| 代幣 | SPL Token（devnet 測試 SKR） | 獎勵與質押 |
| RPC | Helius 或 QuickNode devnet | 交易送出與查詢 |
| 靜態資產 | Arweave／IPFS 或 CDN | 跑鞋圖片與 metadata JSON |

### 9.2 打卡資料流
1. App 從 Health Connect 讀取步數／睡眠，並附 dataOrigin。
2. App 產生感測器特徵摘要（不上傳原始軌跡，僅統計值）。
3. App 以錢包簽署請求（證明錢包所有權）送至後端。
4. 後端執行 FR-07 規則，通過後簽發證明：`{wallet, date, task, amount, expiry}`。
5. App 組交易：前置 ed25519 驗證指令 + `clock_in` 指令。
6. 鏈上程式檢查證明簽章、日期未領取、金額上限，從金庫轉出 SKR，更新跑鞋經驗值。

### 9.3 鏈上帳戶（草案）
- `Config`：管理員、attestor 公鑰、金庫、每日上限。
- `PlayerProfile`（PDA by wallet）：跑鞋 NFT 位址、核心等級、經驗值、最後打卡日、連續天數。
- `Tournament`（PDA by week）：獎金池、參賽人數、狀態。
- `TournamentEntry`（PDA by tournament + wallet）：質押金額、最終步數、名次。

### 9.4 決策點
- D-01 【待確認】獎勵發放走「鏈上程式驗證證明」（去信任、Demo 更有說服力）或「後端直接轉帳」（實作快）。建議前者，且在第二週先做最小版本。
- D-02 【待確認】NFT 標準：Metaplex Core 較輕量且支援可更新屬性，建議採用。
- D-03 【待確認】後端託管位置與是否需要 Seed Vault 相關展示。
- D-04 【已確認】平台範圍為 Android 單一平台，iOS 不在範圍內。詳見 5.0。此決策已定案，後續需求變更不得重新引入 iOS 相容性工作。

## 10. 非功能需求

| 類別 | 需求 |
|---|---|
| 效能 | 主儀表板冷啟動 ≤ 3 秒；交易簽章往返 ≤ 5 秒 |
| 可用性 | 後端可用率黑客松期間 ≥ 99%；離線時可查看快取資料 |
| 安全 | 後端私鑰以環境變數或 KMS 保管；證明含到期時間（≤ 10 分鐘）與 nonce；鏈上程式限制 attestor 公鑰可由管理員更換 |
| 隱私 | 不上傳原始 GPS 軌跡；健康資料僅保留 30 天；提供刪除資料選項；符合 Health Connect 與 dApp Store 隱私政策要求 |
| 相容性 | Android 單一平台；最低 Android 14（API 34，Health Connect 內建），Seeker 為主要測試機。不驗證 iOS 相容性 |
| 可維護性 | 防作弊參數與代幣參數以設定檔管理，可不重新部署調整 |
| 可觀測性 | 後端記錄每次驗證結果與拒絕原因 |

## 11. 假設、限制與依賴

**假設**
- 團隊【待確認】人數與分工足以在四週內完成 App、後端與鏈上三個部分。
- 至少一台 Seeker 實機可供測試。
- 黑客松允許 devnet 提交，且評審接受測試用 SKR。

**限制**
- MWA 僅支援 Android，加上 Health Connect 為 Android 專屬，因此本次確定為 Android 單一平台（5.0）。
- Health Connect 背景讀取需 Android 14 以上並經使用者授權，部分機型會限制背景執行。
- 睡眠資料無法以 GPS 或陀螺儀交叉驗證，只能做來源與合理性檢查。

**依賴**
- Health Connect SDK、react-native-health-connect。
- Solana Mobile SDK（MWA、Seed Vault）。
- Anchor、Metaplex 程式庫。
- devnet RPC 服務。
