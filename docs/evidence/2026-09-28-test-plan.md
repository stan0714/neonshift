## 1. 為什麼是這個順序

有三道閘門，開了才有東西可測：

| 閘門 | 現況 | 開了之後解鎖 |
|---|---|---|
| ① 部署後端（migration 0019／0020／0021 ＋ 新版 API） | `healthz` 200 但 `/v1/seasonal` **404** | 節日全部、分享計數、活動流程 |
| ② 鏈上程式升級（**不可逆，你自己執行**） | 已部署的程式 `CATEGORY_MAX = 13`，拒絕 seasonal | 節日鑄造與揭曉動畫 |
| ③ 外出實跑 ≥5 km | — | COMP-W02 主線、GPS 長時間 |

所以順序是：**先把不需要任何閘門的做完（A 組，今天就能做）→ 開閘門①（最划算，一次解鎖三組）
→ 閘門② → 閘門③**。提交影片排最後，因為它要錄的是前面已經通過的畫面；先錄會白錄。

## A 組 · 現在就能做（不需部署，約 90 分鐘）

### A-1 冷啟動獨立運行（APK-03）
1. `adb shell am force-stop cc.neonshift.app`，拔掉 USB，確認 Mac 上沒有 Metro 在跑。
2. 從桌面圖示開啟，走一遍：Home → Gear → Arena → Explore → Profile。
3. 插回 USB，`adb logcat -d | grep -iE "FATAL|AndroidRuntime|ReactNativeJS"`。

**算過**：五個分頁都能開；logcat 無 `FATAL`／無 JS 例外。

### A-2 鏈上讀取錯誤卡（9/27 新增，第一次上實機）
1. 在 Home，手動開啟飛航模式（`settings put global airplane_mode_on` 在一般權限下不生效，用手撥）。
2. 下拉重新整理。
3. 關掉飛航模式，再重新整理。

**算過**：錯誤卡正文是**一句人話**（「連不上」那一類），畫面上**看不到** `jsonrpc`、
`{"error"`、或任何 base58 帳號位址；技術細節只出現在一行 `Ref …`。關掉飛航後自動恢復。
**要特別看**：以前這張卡會把整段 `{"jsonrpc":"2.0","error":{"code":504…}}` 貼在正文。

### A-3 分享卡六種（PG-SHARE-06／07／09，第一次上實機）
對每一種各存一張圖：運動摘要、成就、跑鞋、守護、**護照**、**完賽**。
其中一種另外測**限時動態尺寸**（1080×1920）。

**算過**：圖上沒有路線（預設）、沒有精確開始時間、沒有錢包位址；文字不溢出、四周留白對稱；
未鑄造的成就卡標示「個人紀錄／尚未驗證」而不是講成收藏；devnet 標示存在。
分享出去後**連結會直接開 App**（今天已驗證網域，這裡順便確認實際分享流程）。

### A-4 錢包九項（evidence 錢包組）
未安裝相容錢包 / 取消授權 / 連點連接 / 背景返回 / 已核准但錢包未回覆 /
session 過期 / 切換帳戶 / 無 SOL / 重開 App 斷線。

**算過**：每一種都有明確訊息且不崩潰；取消不寫入 session；連點只開一次錢包；
切換帳戶後舊帳戶資料不混入；無 SOL 時**在送出前**就提示。

### A-5 UI 六項
冷啟動直接進 Home（有 session）/ 窄螢幕與字體放大無截斷 / 中英切換兩語完整 /
Reduce Motion 直接顯示結果 / 返回鍵不卡死 / 舊路線背景不隨偏好改變。

**算過**：中英切換後**沒有任何畫面出現英文 key 或空白**；Reduce Motion 開啟時
揭曉動畫直接顯示結果（不是播完再顯示）。

### A-6 打卡冪等與 UTC 換日（APK-07）
1. 完成一次步數打卡，記下交易簽章。
2. 立刻再按一次打卡。
3. 跨 UTC 00:00 前後各看一次任務狀態。

**算過**：第二次被 receipt 擋下（顯示已領取），**不產生第二筆發獎**；UTC 換日後任務重置、
步數基準正確。

### A-7 運動離線保存與依序同步
1. 飛航模式下錄一段短運動（室外，2～3 分鐘），結束。
2. 再錄兩段，共三筆未同步。
3. 恢復網路。

**算過**：三筆都在本機保留；恢復網路後**由舊到新依序同步**，不跳過、不重複；
任一筆缺口大時標為待審而不是直接算成正式資格。

### A-8 NFT 領取六項（PB／里程碑，現有鏈上程式已支援）
未達標不可領 / 待 registry 顯示等待 / 取消簽章無交易 / 成功領取 Explorer 查得到 asset /
重複領取被 receipt 擋下 / **回覆遺失後查 receipt 正確顯示**。

最後一項的做法：在錢包已簽送出、App 還在等確認時切飛航模式，然後殺掉 App 重開。

**算過**：重開後 App 自己判定出結果（已領取／確認中），**不會重送交易**，也不會顯示成失敗。
這條路徑今天剛加了退避重試（`806867e`），但**那個 commit 還沒出包**——這一項要測的是
目前包裡的行為；若這裡出現「錯誤而不是結論」，就是 `806867e` 要修的那個情況，重新出包後再測一次。

### B-1 節日足跡讀取
開 Gear → 收藏 → 節日。

**算過**：**先前那個「節日足跡讀取失敗」警示消失**。三屆 `enabled` 都還是 `false` 時，
這一區會是空的但不報錯——那是正常的。

### B-2 節日提醒訂閱與本機排程通知（9/28 新增，最需要實測的一項）

先在 `backend/seasonal/campaigns.json` 打開一屆。**想在兩分鐘內看到通知真的響**，
把那一屆的窗口設成「開始時間 = 現在 + 7 天 + 2 分鐘」——`soon` 通知就排在 2 分鐘後
（排程時刻是 `starts_at − 7 天`）：

```bash
# 改完一定要先驗設定（它會把 UTC 窗口換算回活動時區的當地日期印出來，
# expect_local_days 對不上就會失敗——每年加新一屆最容易錯的就是這裡）
cd backend && npm run seasonal:check
# 通過後才部署
```

手機上：
1. 收藏 → 節日 → 打開那一屆的「開始前提醒我」。**第一次**應該會出現系統通知詢問
   （這台機器已經是 granted，所以不會再問——這是正常的，不是失敗）。
2. 確認開關下方文案是「開始前 7 天、窗口開啟與窗口結束各提醒一次…」，
   **不是**舊的「只會在你打開 App 時提醒」。
3. 驗證排程真的進了系統：
   ```bash
   adb shell dumpsys alarm | grep -c cc.neonshift.app        # 應 > 0
   adb shell dumpsys notification | grep -o "mId='seasonal-reminders'"   # 頻道已建立
   ```
4. 把 App 切到背景（不要殺掉），等 2 分鐘。
5. 通知出現後：關掉那一屆的提醒開關，再查 `dumpsys alarm`。

**算過**：
- 通知出現在系統通知列，**小圖示是單色脈衝**（與運動中那個同一張），色票 mint。
- 通知文字是屆名＋年份＋期限，期限以**活動時區**顯示。
- 點通知會開 App。
- 步驟 5 之後 `dumpsys alarm` 裡那些鬧鐘**消失**——關了開關就不該再被通知。
  （這正是 `806867e` 修的破口，所以這一項要用**重新出包後**的 APK 測。）
- 切換 App 語言後，未來的通知文字跟著換語言（再查一次 `dumpsys alarm` 會看到重排）。

### B-3b SKR 外觀付款 · devnet 完整流程（2026-09-29 起是**領 SKR 獎的條件**）

主辦方 9/29 回覆：devnet＋tSKR 可參加 SKR 獎，條件是「整合邏輯健全且**清楚呈現**」。
所以這一組從「有空再測」變成提交階段必做——SKR-07 的主網小額實測則移到得獎後。

前提：`/etc/neonshift/api.env` 加上 `SKR_ENABLED=true`、`SKR_NETWORK=devnet`、
devnet 測試 mint（`scripts/chain/skr-test-mint.sh` 產生）、`SKR_RECIPIENT`（收款錢包公鑰，
keypair 在 `~/.config/neonshift/skr/recipient.json`，600）、`SKR_GENESIS_FRAME_PRICE`。
啟動 log 應印 `SKR ready`；印 `SKR 停用：…` 就是設定沒過，不要往下測。

1. 用**沒有**首次 5K 資格的帳號看 Genesis Mint 邊框 → 應顯示 `Requires a verified first 5K`，不可購買。
2. 用有資格的帳號購買：確認框要同時顯示**金額、網路、收款人**；畫面全程可見
   `TEST SKR · devnet · not official SKR`。
3. 錢包簽署 → 確認中 → 已解鎖。記下訂單 id、交易簽章、收款 ATA。
4. 餘額不足 / 無 SOL / 取消簽章 各測一次。
5. 付款送出後立刻殺掉 App，重開（測 SKR-05 的查單恢復）。
6. 重裝 App 後重新登入同一錢包（測 SKR-06 的權限恢復）。

**算過**：
- 無資格不可購買；有資格可購買且**確認框三項齊全**。
- 付款確認後邊框在該錢包永久可用，**重裝與登出後仍在**（權限以伺服器為準）。
- 殺掉 App 再開能查回同一張訂單，**不重扣**。
- 三種失敗各有可理解的訊息且可恢復。
- 全程畫面看得到這是 devnet 測試代幣——**不得把 devnet 付款呈現成主網成功**（影片同一原則）。
