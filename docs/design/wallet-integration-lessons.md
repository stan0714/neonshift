# 行動端錢包整合：踩過的坑

2026-09-23｜整理自 NeonShift（React Native ＋ Solana Mobile Wallet Adapter ＋ Seeker 實機）。
寫給**要在別的專案接錢包的人**，不需要讀過本專案原始碼。每一條都是實際撞到並修過的，不是「最佳實務」清單。

標記：**[MWA]** ＝ Solana Mobile Wallet Adapter 專屬；**[通用]** ＝ 換成任何「跳出去外部 App 簽名再跳回來」的整合都成立（含 WalletConnect、各家 deeplink 錢包）。

---

## 最貴的三個教訓

### 1. 「使用者簽完了」不等於「你收得到結果」 [通用]

這是所有錢包整合的核心難題，而且**測試環境永遠不會告訴你**。

實際遇到的：Phantom 26.6 在 Seeker 上，Seed Vault 已完成簽章、交易也送出去了，但 `sol_mwa_sign_messages` 在錢包端內部錯誤，**永遠不回覆**呼叫端。App 那邊看到的只是一個永遠不 resolve 的 Promise。三次重現，換 Seeker Wallet 就正常。

所以整個架構的前提必須是：

> 錢包沒回覆時，**結果是未知，不是失敗**。

把「未知」當成「失敗」會做出最糟的事——顯示「領取失敗，請重試」，使用者重試，於是付兩次錢或鑄兩枚 NFT。

**做法**：定義一個獨立的錯誤碼（我們叫 `WALLET_NO_REPLY`），跟「使用者拒簽」「錢包沒安裝」分開。收到它時，呼叫端一律去**查真相來源**（見第 2 點），不是重送。

### 2. 交易結果的真相來源是鏈，不是你的 Promise [通用]

每一個會改變狀態的操作，都要有一個「做完了沒」的**可查詢憑證**，而且要在送出交易**之前**就能算出來。

我們用 PDA（程式衍生位址）當 receipt：
- 送出前先查 receipt 在不在 → 在就直接回「已完成」，連錢包都不用開
- 送出後逾時／錯誤 → 再查一次 receipt → 在就是成功
- 只有「原交易確定失敗」**且** 超過 `lastValidBlockHeight` **且** receipt 不存在，才可以重建新交易

絕對不要拿同一筆已簽章的交易盲目重送。

換到別的鏈也一樣：找一個能事前決定、事後查詢的識別（訂單 id、nonce、idempotency key），server 端就用它做冪等。

### 3. 錢包是另一個 App，它有自己的設定，而且會跟你不一致 [通用]

實機上跳出來的是：

```
Network mismatch
Your current network is set to mainnet, but this transaction is for devnet.
```

錢包掛在主網，我們的交易是 devnet。**App 無法改錢包的網路設定**，只能在錯誤訊息裡告訴使用者去哪裡改。

一般化：錢包端的狀態（網路、帳號、鎖定、版本）你都控制不了，只能偵測與說明。所以：
- 授權時就把 chain 綁死（MWA 的 `authorize({ chain: 'solana:devnet' })`），讓不一致盡早暴露
- 錯誤文案要**指向解法**（「到錢包設定切換到 devnet」），不是「交易失敗」
- 如果你的產品同時要用兩條鏈（我們有 devnet 主流程＋主網付款），**兩條鏈各自授權、各自存 token**，不要共用，也不要偷偷改全域 cluster

## 授權與 session

### 開機時不要 reauthorize [MWA]

MWA 的 `reauthorize` 會**把錢包 App 拉到前景**。放在 App 啟動流程裡，使用者一開 App 就被彈到錢包，體驗災難。

做法：啟動時只讀本機保存的 session 顯示「已連接」，真正的 reauthorize 延後到**第一次需要簽章時**。

代價要講清楚：本機有 token **不代表現在還能簽**。UI 不可以因為有 session 就宣稱可以簽章。

### 重新授權失敗要重開一次全新授權，但中間要等 [MWA]

錢包撤銷／清除 token 之後的行為各家不同（Phantom 直接關 session，Seeker Wallet 回 `-1 ERROR_AUTHORIZATION_FAILED`）。偵測到就改開一次全新授權讓使用者確認。

**坑**：立刻重開會失敗。錢包關閉上一個 session 後還在收尾（Phantom 會重建本機 WebSocket server），新的 session 會被一併關掉。我們固定等 **1.5 秒**再重試，才穩定。

重試只能發生在**授權階段**。操作已經送到錢包之後的錯誤要原樣拋出，不能重送。

### 回來的帳號必須驗 [通用]

重新授權後錢包可能回一個**不同的帳號**（使用者在錢包裡切換過）。一定要比對位址，不同就清掉本機 session 當作過期，不要默默用新帳號繼續——否則資料會寫到錯的錢包。

### 斷線時本機優先 [通用]

`deauthorize` 可能失敗或不回覆。不管錢包端結果如何，**本機 token 一律清除**。使用者按了中斷連接就是要斷。

### 本機儲存會壞 [通用]

SecureStore 寫入可能失敗，讀到的 JSON 可能合法但欄位損壞。
- 讀取時逐欄驗證（token、位址、URI），無效就當作未連接，**不要開錢包**
- 寫入失敗要有獨立錯誤碼（我們用 `STORAGE_ERROR`），文案講「裝置保存失敗」，不要混進錢包錯誤

## 簽章往返：回不來怎麼辦

### 用 App 前景狀態當訊號，比純逾時聰明 [通用]

純 `Promise.race` 逾時很難調：設太短，使用者還在錢包裡讀交易內容就被取消；設太長，卡住的情境要等很久。

我們的做法（`app/src/services/wallet/mwaGuard.ts`）：

| 訊號 | 行為 |
|---|---|
| App 回到前景後 **8 秒**仍無回覆 | 判定 `WALLET_NO_REPLY`。使用者都回來了錢包還沒回話，就是不會回了 |
| 絕對上限 **120 秒** | 任何情境的兜底 |
| 回前景後又切去錢包 | **取消**寬限計時。使用者是自己切回去繼續操作的 |

這個組合在實機上比單一逾時準很多。

### 放棄之後，原生 session 還活著 [MWA]

JS 端放棄不等於原生端結束。MWA 原生 `invoke` 有自己的 90 秒逾時，在那之前它可能還佔著互斥鎖，下一次開錢包會失敗。

我們記一個 `staleUntil()` 時間戳，UI 在這段期間提示「上一個錢包工作階段尚未結束」，而不是讓使用者按了沒反應。

**另一個坑**：不要試圖在 `transact` 回呼裡呼叫原生 `endSession`——`transact` 的 finally 會再呼叫一次，第二次在原生層丟例外。只能在 JS 側守門。

### 晚到的結果一律丟棄 [通用]

放棄之後錢包突然回覆了，**不可以**拿這個結果去寫登入狀態或授權。那時 App 可能已經走到別的狀態。丟掉，讓呼叫端用查詢真相來源的路徑收斂。

### 分階段顯示，不要一路 loading [通用]

「開啟錢包 → 核准 → 簽訊息 → App 登入 → 保存」五個階段分開顯示，失敗時**停在失敗的那一階段**。使用者才知道是錢包沒開，還是簽完了但登入失敗。

每個階段等超過 12 秒，補一句「請檢查錢包是否有待核准的請求，然後返回 App」。

**鑄造流程同理**，而且有個硬規則：**只有錢包真的回傳 signature 之後，才能顯示「已送出」**。在那之前顯示成功就是騙人，使用者會關掉 App 以為完成了。

## 後端狀態落後於鏈

我們的後端靠 indexer 掃鏈上事件才把成就標成 `minted`。錢包確認到 indexer 追上之間有空窗。

App 在鑄造完成的當下重抓伺服器資料，拿到的還是舊狀態 → 卡片又畫成「可鑄造」，**等於在邀請使用者重複鑄造**。

做法（`app/src/services/chain/localMints.ts`）：鑄造成功後，App 先採信自己手上的交易簽章與 asset，套用在伺服器回應上，直到 indexer 追上。原則：

- 伺服器一旦標為已完成 → 丟掉本機樂觀狀態，之後完全以伺服器為準
- 伺服器說**撤銷** → 一律以伺服器為準，樂觀狀態不得覆蓋（撤銷是更新的事實）
- 只存在記憶體，不要持久化。重開 App 時 indexer 早就追上了

這條在任何「鏈上先成立、後端非同步跟上」的架構都會遇到。

## UI 狀態與競態

這些在實機上都真的發生過：

| 問題 | 處理 |
|---|---|
| 使用者連點 connect → 同時開啟多個 MWA session，回覆互相覆蓋 | Store 合併進行中的請求；已連接就不再開錢包 |
| 啟動時的 restore 比新的 connect 晚返回 → 覆蓋掉新帳號 | 用 revision 序號，舊的結果不覆蓋新的 |
| 錢包連上了但 App 登入失敗，錯誤被吞掉 | 保留錢包連接但明確顯示「App 登入尚未完成」，給使用者一顆繼續的按鈕 |
| 錢包通訊失敗被說成「區塊鏈故障」 | 分清楚：通訊中斷 ≠ 鏈壞了。不要替鏈背鍋 |
| 沒收到回覆卻顯示「沒有簽章成功」 | 刪掉所有未經證實的結論，改成「請先查詢結果」 |

### 記錄中不要彈錢包 [通用]

我們有 GPS 記錄運動的流程。**運動記錄中出現錢包彈窗**會中斷記錄、可能掉資料。這條列為驗收必驗項。

為此做了一個錢包互動時間線（`walletTimeline.ts`），記錄每次操作的等待時間、結果、以及**是否發生在記錄中**，在 Profile 顯示摘要（不含位址與簽章）。實機驗收時直接看「運動中 0 次」。

如果你的 App 有任何不能被打斷的流程（錄影、上傳、計時），建議做同樣的事——否則你只能靠使用者回報。

## 登入（簽訊息換 session）

### 已簽好的訊息要能重用 [通用]

流程是：取 nonce → 錢包簽 → 送後端 verify。

**坑**：verify 因為網路失敗時，如果直接從頭再來，使用者要**再簽一次**。很煩，而且沒必要。

做法：已簽好的 `(message, signature)` 在 nonce 有效期內保留著，下次重試直接 verify，不再開錢包。只有 nonce 用掉／過期／簽章無效才重走完整流程。

### 後端該做的 [通用]

- nonce：32 bytes CSPRNG、**只存雜湊**、短 TTL（我們用 5 分鐘）、**一次性**
- 訊息裡綁 domain 與 uri，防跨站重放
- 敏感操作（發布、核銷、權限變更）額外要求**近期登入**（我們用 30 分鐘），不是有 token 就放行
- 授權一律查資料庫的即時角色，**不要信 client 傳來的 role 或過期 JWT 裡的欄位**

## 各家錢包的實作差異（會咬人）

| 差異 | 實際影響 |
|---|---|
| `minContextSlot` | Phantom 的 MWA 實作當**必填**，缺少直接拒絕而且**不顯示簽章畫面**（看起來像沒反應）；Seeker Wallet 可選 |
| 授權失效的回報 | Phantom 直接關 session；Seeker Wallet 回 `-1` |
| Seed Vault 簽完不回覆 | Phantom 26.6 on Seeker 必現（見最上面） |
| 網路設定 | 各家位置不同，有些消費者版根本沒有 devnet 選項 |

**結論**：不要只測一個錢包。至少兩個，而且要在**真機**上測——模擬器測不到跨 App 跳轉的絕大多數問題。

## 驗收清單：錢包失敗矩陣

每一項至少實機跑一次，每一項都要有明確狀態、可重試、且**不會重複扣款／重複發放**：

- [ ] 使用者拒簽
- [ ] 簽完後不回 App（停在錢包畫面 8 秒以上）
- [ ] 簽署過程中手動切回 App，再切回錢包完成
- [ ] 在錢包裡換成另一個帳號後再簽
- [ ] 帳號沒有足夠的手續費
- [ ] 錢包網路與交易網路不一致
- [ ] 錢包沒安裝
- [ ] 送出後立刻關掉 App，重開能否恢復狀態
- [ ] 連點按鈕
- [ ] 飛航模式下操作，恢復連線後的狀態

---

## 如果只能記三件事

1. **沒回覆 ≠ 失敗。** 結果未知時去查鏈，不要重送。
2. **每個狀態變更都要有事前可算、事後可查的憑證。** 沒有這個，冪等就是空談。
3. **真機、至少兩個錢包。** 這一段的坑幾乎沒有一個是在模擬器上發現的。
